# 材料智能服务开发、开服与前端对接规范

> 面向对象：新加入材料服务开发、算法、测试和运维工作的同事。
>
> 目标：所有服务以相同方式开发、调试、上线和交接；既能稳定对接网页，也能让后来维护的人快速理解代码、配置和运行状态。

## 1. 先记住的原则

1. 一个服务只解决一个明确业务问题。先确认服务边界、输入和输出，再开始实现。
2. 浏览器请求、业务编排、领域计算、数据读取、模型调用、资产上传必须分开；不要把所有代码写进一个文件。
3. 已联调的前端协议是契约。未与前端确认前，不改路由、字段、事件顺序、文本标记、图片/GLB/文件类型。
4. 密钥只放服务自身本机 `.env`，绝不提交 Git、绝不写入日志、绝不从别的服务借用 `.env`。
5. 调试期使用 tmux；通过验收、长期稳定运行后，统一由 `service` 管理。
6. 机器学习、代理模型或数据库推断必须说明证据等级，不能表述为实验或 DFT 的最终结论。
7. 删除旧代码、旧配置或兼容逻辑前，先证明它没有调用方，并补齐测试和交接记录。

## 2. 推荐服务结构：职责是硬要求，目录不是

下图是新服务的**推荐目标模板**，不是要求所有既有服务立刻拥有完全相同的目录树，也不是要求为了对齐而新建空目录或搬迁已验证代码。

- 新服务：可直接按此模板建立目录；
- 已运行服务：先保持实际启动链路、前端契约和产物路径稳定，只在新增代码或有明确收益的整改中逐步按职责归位；
- 小型服务：允许合并目录，例如暂不单独建立 `application/` 或 `presentation/`；
- 无论目录形态如何，`main.py` 的传输职责、`team_config.py` 的编排职责、领域计算、I/O/存储和展示资产的职责边界必须保持清晰。

因此，下面的目录名称是推荐位置，不是“文件必须叫这个名字”的硬编码要求：

```text
<service_name>/
├── main.py                     # HTTP/WebSocket 入口与启动入口
├── src/
│   ├── team_config.py           # 服务级编排：展示完整业务执行顺序
│   ├── application/             # 用例流程：查询、生成、筛选、评估、结果组装
│   ├── domain/                  # 领域模型、约束、计算、评分、排序等纯业务规则
│   ├── infrastructure/          # 数据库/文件、外部 API、模型进程、对象存储
│   ├── presentation/            # Markdown、图表、展示资产说明
│   ├── contracts/               # 内部请求、结果、manifest 和校验模型
│   ├── compat/                  # 历史路径、旧字段、旧角色名的临时兼容层
│   └── settings.py              # 环境变量转换为服务配置
├── data/                        # 服务维护的数据及来源、字段说明
├── assets/                      # 服务自有字体、静态模板等
├── results/                     # 运行结果，必须 Git 忽略
├── tests/                       # 单元、契约、冒烟测试
├── docs/                        # 接口、数据、运行和交接文档
├── .env                         # 本机配置和密钥，必须 Git 忽略
├── .env.example                 # 无密钥配置样例
└── README.md                    # 最短启动和使用说明
```

代码依赖方向必须保持单向：

```text
网页 / 网关
  -> main.py（传输与协议）
  -> src/team_config.py（服务编排）
  -> application（用例）
  -> domain（规则） + infrastructure（I/O 与外部能力）
  -> presentation（文本与资产清单）
  -> main.py（按前端协议发送结果）
```

## 3. 每一层应该做什么

| 位置 | 应做的事 | 不应做的事 |
|---|---|---|
| `main.py` | 加载本服务 `.env`、创建 HTTP/WS 路由、校验传输请求、发送前端事件、统一错误处理、启动服务 | 读 CSV、直接跑模型、拼复杂科学规则、上传对象存储 |
| `src/team_config.py` | 用中文清楚写出“阶段 1/2/3”的服务流程，选择用例，合并结果和可追溯信息 | 处理 WebSocket 帧、读取密钥、直接操作数据库/MinIO/子进程 |
| `application/` | 完成一次完整业务用例，例如“规范化请求→查询→筛选→组装结果” | 硬编码前端文本标记或 URL 路由 |
| `domain/` | 约束、材料领域对象、算法规则、评分和排序 | 导入 FastAPI、读取环境变量、访问网络或文件 |
| `infrastructure/` | 数据读取、外部模型/API、GPU/子进程、文件系统、对象存储 | 决定业务优先级或夸大科学结论 |
| `presentation/` | 用户文字、表格、图表、本地资产描述 | 直接上传对象存储或发送 WebSocket |
| `compat/` | 有明确删除条件的旧协议/旧字段适配 | 新业务的常规实现 |

`team_config.py` 的作用是让评审者从上到下看懂服务如何运行，而不是成为“大杂烩”。推荐直接按阶段写清注释和调用顺序：

```python
# 阶段 1：标准化请求与必要信息校验
# 阶段 2：执行领域用例（查询/生成/筛选）
# 阶段 3：组织可追溯结果与资产清单
# 阶段 4：返回内部标准结果，由 main.py 转为前端事件
```

不需要为了形式再额外包一个名字叫“编排器”的函数；关键是职责和顺序清楚。

## 4. 命名规范

- 目录、Python 包、模块、函数、变量：全小写 snake_case，如 `material_discovery`、`candidate_ranking.py`。
- 类：PascalCase，如 `CandidateRankingService`。
- 常量、环境变量：UPPER_SNAKE_CASE，如 `SERVICE_PORT`、`MINIO_ENDPOINT`。
- HTTP 路径、外部服务标识：全小写 kebab-case，如 `/material-discovery/start`。
- tmux session 与系统服务名采用稳定、可读格式：`material-<capability>-<port>`；例如 `material-discovery-<port>`。
- 不使用个人名、含义不明的缩写或泛化文件名。生产代码中禁止新建 `utils.py`、`temp.py`、`new.py`、`test2.py`。
- 名称一旦成为前端、网关、对象存储或上游服务契约，不能直接全局替换；必须经过兼容期和契约测试。

## 5. 配置、数据与资产

### 5.1 `.env`

- `main.py` 必须从服务根目录显式加载该服务的 `.env`，不可依赖终端当前目录。
- `.env` 只保存端口、密钥、模型路径、外部数据位置和部署差异；必须写进 `.gitignore`。
- `.env.example` 只提供字段与说明，绝不出现真实 API key、访问密钥、密码、内网凭据或个人路径。
- 一个服务只使用自己的环境变量和凭据。禁止 `MINIO_CREDENTIALS_FILE`、字体路径、模型路径指向相邻服务。
- 不将机器绝对路径、Conda 环境、bucket 名或公网域名写进领域规则；它们应由 `.env` 提供。

对象存储的推荐最小配置：

```dotenv
MINIO_ENDPOINT=http://host:port
MINIO_ACCESS_KEY_ID=仅放在本机 .env
MINIO_ACCESS_KEY_SECRET=仅放在本机 .env
MINIO_REGION=us-east-1
MINIO_SECURE=false
PICTURE_PUBLIC_BASE_URL=https://public-host/path/to/images
```

### 5.2 数据、结果和文件资产

- `data/` 保存服务自有数据及其版本、来源、字段含义；大模型权重、原始大数据不提交 Git。
- `results/`、日志、缓存、临时 CIF、PNG、GLB、上传文件都是运行产物，应 Git 忽略并定期清理。
- 每个任务结果至少保存：任务 ID、输入摘要、状态、模型/数据版本、结果、证据等级、资产清单与失败原因。
- 字体、图表模板等放在本服务自己的 `assets/`，不从其他服务目录读取。
- 先生成本地文件，再上传对象存储或通过任务资产路由提供。上传失败必须记录原因并按约定回退；不能返回虚假的公开 URL。

## 6. 网页、HTTP 和 WebSocket 约定

### 6.1 连接网页

网页经网关或直连访问服务。开发环境通常使用：

```text
ws://<host>:<port>/<service-path>/start
http://<host>:<port>/health
http://<host>:<port>/roles
```

生产网页经 HTTPS 网关时使用 `wss://`。前端不得硬编码开发机 IP、临时端口或本地目录；网关、端口和路径由部署配置统一管理。

WebSocket 建连后，客户端首先发送一个 JSON 对象。服务要兼容约定的请求字段并进行校验；不能只依赖某一个偶然字段，也不能把完整敏感上下文写入日志。

### 6.2 成功事件顺序

当前聊天页面依赖以下逻辑顺序。项目若已有不同的已验证契约，以实际契约为准并补充契约测试。

```text
1. 文本帧： [start]
2. JSON 帧：progress（可发送多条）
3. 文本帧：<<<CONTENT_START:<step_id>>> ... <<<CONTENT_END:<step_id>>>
   可在内容区块内穿插约定的 Markdown 展示内容
4. JSON 帧：资产事件（如有）
5. JSON 帧：result
6. 文本帧： [end]
```

- `[start]`、`[end]`、`<<<CONTENT_START:...>>>`、`<<<CONTENT_END:...>>>` 是页面解析标记，不能擅自改写、遗漏或调换顺序。
- JSON 事件至少包含 `version`、`agent`、`type`、`data`；有任务号时带 `request_id` 或 `taskid`。
- `progress` 的 `data` 建议包含 `id`、`stepId`、`title`、`status`、`description`；同一事件中 `id` 与 `stepId` 保持一致。
- 异常使用 `type: "error"` 的 JSON 事件说明原因，再安全关闭连接。客户端主动断开不应记为服务计算失败。

### 6.3 图片、GLB 和文件

- 前端资产事件必须包含步骤 ID、名称、说明、`url` 和 `type`。
- `type` 只能使用双方已约定的值，例如 `MaterialsPNG`、GLB 或文件类型；不得把图片当成 GLB，也不得仅靠文件扩展名猜测。
- 可用 Markdown 图片作为聊天兼容展示，但不能取代结构化资产事件。
- 资产公开 URL、对象 key、类型和发送顺序都属于前端契约。修改前必须抓取完整 WS 帧，与前端联调并更新契约测试。

### 6.4 HTTP 接口

- 每个服务应提供健康检查、角色/能力发现和服务命名空间下的业务接口。
- 任务和资产路由要按服务命名空间隔离，例如 `/service-name/tasks/{taskid}/assets/{asset_name}`。
- 上传接口必须校验文件类型、大小、任务归属和保存路径；客户端文件名不能直接拼为本机路径。
- 修改响应字段时，先保留兼容字段或发布版本号，不能静默破坏网页或上游调用方。

## 7. 开发调试：tmux

### 7.1 何时使用 tmux

开发、排错、联调和短期验证阶段使用 tmux。一个服务一个 session，命名统一为：

```text
material-<capability>-<port>
```

例如：`material-discovery-<port>`。

启动前必须确认：

1. 本服务 `.env` 存在、密钥完整且未上传 Git；
2. 端口未被占用；
3. 激活的是服务实际依赖的 Python/Conda 环境，而不是系统 Python；
4. 所需模型、数据、对象存储和 LLM（如需要）可用；
5. 没有正在处理的用户任务，才执行重启。

调试启动的原则是：先进入服务目录，再激活环境，再运行入口；不要从父目录或任意目录依赖相对路径启动。

```bash
cd /path/to/<service_name>
conda activate <service_environment>
python main.py
```

tmux 调试验收至少包含：健康检查、角色接口、一条最小 WebSocket 请求、最终 `result`、图片/GLB/文件展示和 tmux 日志。

## 8. 稳定服务：统一使用 `service`

当服务完成开发验收、前端联调和连续稳定运行验证后，不再依赖人工 tmux 会话常驻，统一交由系统服务管理：

```bash
sudo service <service_name> start
sudo service <service_name> status
sudo service <service_name> restart
sudo service <service_name> stop
```

每个稳定服务应有唯一、规范的系统服务名，建议：

```text
material-<capability>-<port>
```

系统服务配置由运维统一维护，至少明确：

- 运行用户和工作目录；
- 正确的 Python/Conda 环境与启动命令；
- 服务自身 `.env` 文件位置；
- 日志输出位置与轮转策略；
- 失败自动重启策略；
- 端口、依赖网络、模型/数据挂载和启动顺序。

上线后排障优先使用 `service status` 和服务日志；只有在临时复现、开发调试或明确的维护窗口，才回到 tmux。不得同时让 tmux 和 `service` 在同一端口运行。

## 9. 测试、日志与交接

每次修改结构、协议、模型调用、存储或配置，至少完成：

1. **单元测试**：领域约束、计算、排序、科学结论边界和异常输入。
2. **契约测试**：路由、初始 JSON、`[start]`、内容区块、资产事件、`result`、`[end]` 的字段和顺序。
3. **冒烟测试**：用服务实际 Python 环境导入 `main.py`，验证 `.env`、模型配置和对象存储配置可加载；不泄漏密钥。
4. **网页联调**：发送一次真实请求，确认文字、JSON、图片/GLB/文件、最终结果和服务日志一致。

日志至少记录任务 ID、请求摘要、执行阶段、候选/结果数量、资产数量、耗时和失败原因。严禁记录密钥、访问令牌、完整隐私输入或完整上游上下文。

每个稳定服务的交接文档必须写明：业务边界、端口、系统服务名、所需环境变量类别、数据/模型位置、对外路由、资产路径、已知兼容项、验证方式和负责人。

## 10. 改名、清理与上线检查表

目录名、服务名、端口、WebSocket 路径、`agent` 名、对象存储 pipeline 和任务结果路径都可能是外部契约。修改前必须：

1. 搜索代码、`.env`、系统服务配置、网关、前端、上游服务、日志和文档中的引用；
2. 先消除代码中的仓库绝对路径，机器差异改由 `.env` 管理；
3. 在维护窗口停止稳定服务，确认无活动任务后再迁移；
4. 更新系统服务工作目录、环境、日志和网关配置；
5. 逐项通过 HTTP、WebSocket、资产和网页验收；
6. 保留兼容映射直至所有调用方迁移完成，再凭引用证据删除旧名称或旧代码。

新服务上线前逐项确认：

- [ ] 业务边界已确认，未重复实现已有服务能力；
- [ ] 结构、命名和职责符合第 2～4 节；
- [ ] `.env`、`.env.example`、数据、模型和资产独立；
- [ ] tmux 调试通过，稳定后已登记规范的 `service` 名称；
- [ ] 前端 WebSocket 文本、JSON、资产和最终结果已有契约测试；
- [ ] 对象存储上传、公开 URL 与失败回退已验证；
- [ ] 科学结论说明证据等级和后续验证边界；
- [ ] README、接口文档、交接文档和负责人信息齐全。

---

当“代码整理”与“已验证前端协议”冲突时，优先保持协议稳定，并通过兼容层、契约测试和前端协作分阶段迁移。不要机械搬目录、全局替换名称或删除看似旧的文件。

## 2. 为什么 GitHub 的目录比服务目录多

目录整理是普通的文件提交：保留根目录的四个服务，增加 `development/`，并更新文档和检查工具。GitHub 按提交里的文件树显示这些目录。75 运行目录仍使用原来的工作文件，所以两处看到的完整目录结构不同。

根目录服务源码按 75 的实际文件收集，包括服务目录里尚未提交的源码；下一版实现从整合版本 `213155c` 收集到开发目录。所有代码使用各自的正常入口，根目录服务与开发副本独立运行。具体差异见[开发改动清单](development_changes.md)。

这次整理使用独立克隆完成，75 服务目录保留原 Git 分支及工作文件。目录区分由文件位置和 README 说明实现，没有设置特殊的 Git 路径映射或自动部署。

## 3. “未提交”和“未推送”是什么意思

| 状态 | 文件在哪里 | 下一步 |
| --- | --- | --- |
| 未提交 | 工作目录中的文件已修改，尚未生成包含这些修改的 Git 提交。 | 检查差异和测试结果，确认本次文件后提交。 |
| 已提交、未推送 | 本地仓库已保存提交，GitHub 仍是此前的版本。 | 核对目标分支和远端最新状态，再推送。 |
| 已推送 | GitHub 已收到该提交。 | 其他人可以查看或拉取；部署状态另看部署记录。 |

“本地”也可以指 75 上的独立仓库副本，而不只指 Windows 电脑。GitHub 文件更新与服务部署分别记录，运行进程加载哪一版代码由部署和启动决定。

## 4. 现在能否直接合并或拉取

2026-10-04 目录结构核对时，GitHub main 为 `da05897`，75 服务目录的 Git HEAD 为 `8ec1d84`，另有 27 个已跟踪文件修改和 30 个新文件。main 保留 `8ec1d84` 的提交历史，当时相差 16 个提交；运行目录还包含这些未提交源码，因此提交号差异不能用来判断服务功能的新旧。

当前核对的 916 个服务代码及配置文件与 GitHub main 根目录一致，范围为 `.py/.json/.yaml/.yml/.toml/.cfg/.ini/.sh`，比较时统一换行符。生产 `.env`、模型和任务结果由服务器单独管理。

当前从独立 main 副本同步指定文件即可。服务目录有未提交编辑，直接在其中 `git pull`、切分支或合并整个仓库可能发生冲突，更新运行文件还会影响下一次进程启动。旧远端分支已归档，后续维护入口是 `main`。

如果以后需要让运行目录也跟踪 main，单独安排一次 Git 工作目录迁移：先保存工作文件和机器配置，确认同事编辑，再逐文件核对、测试和验证启动路径。日常代码推送可以先使用下节流程。

## 5. 以后在 75 改完代码，怎样推送

可以从 75 推到 GitHub。推荐继续分开使用“服务运行目录”和“main 发布副本”，按以下步骤维护：

1. 使用跟踪 `origin/main` 的独立仓库副本。先检查分支、工作文件和远端更新；发布副本已有修改时先明确这些文件的归属，再准备本次同步。
2. 列出本次需要同步的源文件，逐项放到对应位置：已经上线并检查通过的代码放根目录服务；开发中或测试通过待部署的代码放 `development/`。保留仓库中其他人的文档、测试和已有更新。
3. 更新相应 README、开发改动说明或部署记录。机器 `.env`、密钥、权重和任务输出继续按服务器资源管理。
4. 查看 `git diff`，运行相关服务测试和文档检查。确认只包含本次文件后执行 `git add`、`git commit`，推送到 `main`。提交标题可写 `fix(1115): 完善结构评价结果说明` 等具体内容。
5. 推送完成后核对 GitHub 提交号和文件。服务部署按[部署记录](deployment_status.md)中的流程单独处理；历史 `backup` 继续固定保存。

新建发布副本可使用正常的 main 克隆，目标目录须为尚不存在的新路径：

```bash
git clone --branch main git@github.com:AI4SciFoundation/Material-Computation.git /data/se42/worktrees/material_service_hub_publish
```

查看发布副本状态时，在该副本根目录执行：

```bash
git branch --show-current
git status --short
git log -1 --oneline
git remote -v
git diff --stat
git diff --check
python3 tools/verify_documentation.py
python3 tools/compare_service_versions.py
```

上述文件比较工具显示根目录与开发目录的区别。`verify_repository_layout.py` 检查 2026-10-04 保存的源码记录；后续升级服务时，保留旧记录，并为新版本建立新的来源和检查记录。

源码同步按实际文件清单处理：确认需要同步的删除操作，保留仓库文档及服务机器配置。后续若需要自动化同步工具，先明确同步目录、文件类型和冲突处理方式。
